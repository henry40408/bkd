# Architecture

## Stack

Go with the standard library `net/http`, `database/sql` over a pure-Go SQLite driver, and `flag` for the command line. Pages are rendered on the server by an escaping string builder in `internal/views`; the CSS and a small enhancement script are in `internal/assets/static/`, compiled into the binary with `go:embed`: no Node build, no CGO. The binary `cmd/bkd` is thin; the code lives in `internal/` packages so tests build the handler directly (`server.New(config).Handler()`). The server was rewritten from Rust; the Rust server's behaviour is the specification, pinned by the captured values that remain in the tests.

## Database

`internal/db` opens the pool and runs the migrations in `internal/db/migrations/` at startup (`migrate.go`, embedded with `go:embed`). The runner writes the `_sqlx_migrations` table, descriptions and SHA-384 checksums exactly as the Rust server did, so an existing database opens unchanged (`createRustDatabase` in `migrate_test.go` pins it). A released migration file is never edited: add a new numbered file. SQL is plain `database/sql` with bound parameters.

Every connection uses WAL, `synchronous = NORMAL`, `foreign_keys = ON` and a 5 second busy timeout. SQLite ignores foreign keys unless each connection enables them, and the cascade deletes below depend on it.

### Schema

- `users`: `username` is 3 to 32 characters of `a-z`, `0-9`, `.`, `_`, `-`, starting and ending with a letter or digit (a `CHECK` enforces it). It is ASCII only because SQLite folds case for ASCII alone, so the `UNIQUE` constraint is case-insensitive on every database. `disabled_at` is a nullable timestamp; `NULL` means active.
- `sessions`: stores a hash of the cookie token, never the token. Deleted with the user.
- `api_tokens` (migration 0008): the same for a token a program sends as `Authorization: Token <token>`. The primary key is the token's SHA-256, `name` is the owner's label (1 to 100 characters), and `last_used_at` is `NULL` until the first use. A token does not expire: it ends when its owner ends it, or when the account is disabled, reset or deleted. Deleted with the user.
- `bookmarks`: every row belongs to one user. Every query must filter by `user_id`. The index `bookmarks_user_url` (migration 0009) is for `FindByURL`, which a browser extension asks on every page it opens.
- `bookmark_tags`: one row per tag. Deleted with the bookmark. The application trims and lowercases tags, because SQLite cannot fold non-ASCII case, so tags may be in any script.

Deleting a user deletes their sessions, bookmarks and tags (`ON DELETE CASCADE`). Timestamps are Unix seconds. Tables are `STRICT`, so a value of the wrong type is rejected.

### Portability

Only SQLite is supported. SQL stays plain so a PostgreSQL port would mostly change the id columns, the case-insensitive username handling and the transaction used to serialize first-admin creation. No database abstraction layer is used.

## Authentication (`internal/auth/`, `internal/users/`)

- `password`: Argon2id with the same parameters as the Rust server (stored PHC strings verify in both directions; `rustPasswordVectors` in `password_test.go`). New passwords need 12 characters (at most 256 bytes) and must not contain the username (compared in lowercase); login accepts any password up to 256 bytes, so an older, weaker password still works. Hashing runs in `Hasher`, which allows at most as many hashes at once as there are CPU cores. For an unknown or disabled user, login must call `Hasher.VerifyDummy` so response time does not reveal which usernames exist. `WarmUp` builds the dummy hash at startup.
- `session`: the cookie holds 256 random bits; the database holds only their SHA-256. Sessions last 30 days and also end after 7 days without use (`last_used_at`, moved forward at most once an hour). A session also records its IP address and `User-Agent` (cut to 200 characters) for the session list, and `confirmed_at`, the last time its owner typed the password (a login counts). Every lookup joins `users`, so a disabled account loses access at once and `is_admin` is never cached. Disabling, deleting or resetting the password of a user must call `RevokeAllForUser`.
- `apitoken`: a token is 256 random bits in hex and the database holds only its SHA-256 (`APITokens.Create` returns the secret once, `Lookup` finds the user by the hash). A token is a password that does not expire, so it must never be logged, listed or returned again after creation; its id for the owner is the first 16 hex digits of the hash, honoured only together with the owner's `user_id`. `Lookup` joins `users` with `disabled_at IS NULL`, so a disabled account loses its tokens' access at once, and records `last_used_at` at most once an hour; a failed write there never fails the request. A user holds at most 20, enforced inside the insert (`INSERT … SELECT … WHERE count < 20`), so two concurrent requests cannot pass the limit. `users.SetDisabled` (when disabling) and `users.ResetPassword` end every token in the same transaction as every session (`revokeEveryCredential`); `ChangeOwnPassword` ends both too, because a stolen cookie can make a token that would outlive every session. Management lives on the Settings page, since the Account page refuses a user the proxy signed in, and a proxy user may need a token most: a program cannot pass the proxy's sign-in page.
- `forwardauth`: a trusted proxy's `Remote-User` header signs a user in on that request alone: there is no cookie and no `sessions` row, so the proxy decides when the user leaves, and `SessionUser.ViaProxy` is true. The header counts only when the TCP peer (not `X-Forwarded-For`) is inside `--forward-auth-trusted-proxies`; it then wins over a cookie. An invalid name from a trusted proxy signs nobody in. `users.AdoptForwarded` finds or creates the account (password hash `!`, which no password verifies), refuses a disabled one, and, when an admin group is configured, sets `is_admin` from `Remote-Groups` on each request. It never demotes the last active admin, and without an admin group the first account of an empty table is the admin: the emptiness check and the insert are one statement in `BEGIN IMMEDIATE` (`db.WithImmediateTx`), like `CreateFirstAdmin`, so two first requests cannot both be admins. Creating it also drops the setup token. A proxy user has no password, so `confirmedAdmin` lets them through, and change-password and confirm answer 403. Without cookies, CSRF protection rests on `sameOriginOnly` and the JSON-only bodies.
- `setuptoken`: 50 random bits shown as `XXXXX-XXXXX` (Crockford base32). It lives only in memory and is compared as HMACs in constant time. Case, dashes and spaces are ignored, and `O`, `I`, `L` read as `0`, `1`, `1`.
- `firstadmin`: one `INSERT ... WHERE NOT EXISTS` inside `BEGIN IMMEDIATE`, so concurrent submissions create exactly one admin.
- `ratelimit`: per-IP, in memory. A caller charges an attempt before checking the secret and refunds it only on success, so parallel requests cannot all pass the check and a success cannot erase earlier failures. Clients are grouped by IPv4 address or IPv6 /64; IPv4-mapped IPv6 addresses count as IPv4. When 10,000 addresses are tracked, new ones are refused until some windows end.
- `username`: the same rules as the `CHECK` in the schema, with ASCII lowercasing first.

## Front end (`internal/views/`, `internal/server/pages_*.go`, `internal/assets/static/`)

- The server renders every page as HTML with the builder in `internal/views` (`html.go` escapes `& < > "` only, byte for byte what the Rust templates produced): `layout.go` has the frames and `errors.go` the shared errors. Each page is one exported function that returns a string. The builder escapes all text; the only unescaped output is the highlighted text, which splits the text first and escapes each part. The app works with JavaScript turned off: every action is a link or a form, and a test suite posts the forms without a script.
- `internal/assets/static/app.css` and `app.js` are served at `/app.css` and `/app.js` with `Cache-Control: no-cache`. `app.js` is progressive enhancement only: it turns a same-origin click or form submit into a `fetch`, parses the HTML answer with `DOMParser` and swaps `main` and the sidebar, keeping the history in step (`pushState`, `popstate`). If anything fails, it falls back to the normal navigation. It also shows `<time>` tooltips in the reader's time zone, grows the list in place on Load more (`replaceState`; ticked rows stay ticked, and a focused link moves the focus to the first new row), opens Edit and Delete as inline panels inside a list row or the random pick (the form is read from the edit or delete page and posted from there; a refusal stays in the panel, Escape or Keep closes it and returns the focus to the link), fills the edit form's URL field from the "Use new address" button of a moved link, makes "/" outside a field focus the search field, reveals what the server marks `data-script-only` (that button, the import drop hint) and lets a file be dropped on the import box. No page needs it.
- Real paths, not hash routes: `/` (the list; `q`, `tag`, `status`, `page`, `select=1`), `/random`, `/bookmarks/{id}/edit`, `/bookmarks/{id}/delete`, `/login`, `/setup`, `/confirm`, `/users`, `/account`, `/transfer`, `/settings` (with `POST /settings/tokens` and `POST /settings/tokens/{id}/revoke`; a made token is answered on the page itself with status 200, never redirected, so the secret is in no address or cookie; without the script the page's address is `/settings/tokens`, and a reload asks the browser to post again, which makes a second token). A form that fails answers with the form again and the error status; a form that works redirects (POST-redirect-GET) with a fixed `?notice=` key that the server maps to text, so a link cannot put words on the page.
- The page handlers and the JSON handlers share the `service_*.go` functions in `internal/server`, so the rules (rate limits, timing guards, session rules, `confirmedAdmin`) exist once. `signedInPage`, `adminPage` and `confirmedAdminPage` (`pages.go`) wrap the guards and turn a refusal into a redirect (`/login`, `/confirm`) or an error page. A page read without a session redirects to `/login?next=<path+query>`, with `&notice=session-ended` only when a session cookie came with the request; `next`, and the `back` value that Edit, Delete and their Cancel/Keep links carry to return to the list, are used only when `sameSitePath` accepts them (a path starting with a single `/`; no scheme, `//`, backslash or control character), else `/`. A refused bulk action shows the list again in select mode with the ticks and an error line.
- Without a script: `?page=N` is cumulative (the list shows the first N times the page size rows, and `bookmarks.Store.Count` gives the total for "Showing S of M"); a "Load more" link to `?page=N+1#bookmark-<id>` returns to the last row shown, and with the script it grows the list in place instead; select mode is `?select=1` with native checkboxes (`id-<n>`) in one bulk form; edit and delete use their own pages; "Check links" runs to the end before the page answers (with the script, it streams `POST /api/bookmarks/check` instead, shows "Checking links: n of N" with a Stop button that aborts the fetch, then reloads the page); Random shows the pick on the list; the mobile menu is a CSS checkbox; times are relative text with the UTC time as the tooltip.
- Pages carry a Content-Security-Policy with `form-action 'self'` and no inline script, style or event handler (a test checks this). `/app.js` and `/app.css` keep `form-action 'none'`.
- CSRF for forms: the session cookie is `SameSite=Lax` (a link from another site opens signed in; only top-level GETs carry it across sites, and no GET changes data), and `formOriginRequired` refuses a post unless its `Origin` equals `Host`. A browser sends `Origin: null` under `Referrer-Policy: no-referrer`, so pages send `Referrer-Policy: same-origin`. The JSON API still lets a request without `Origin` through (only a script can send one).

JSON under `/api`. Handlers are thin: `api_*.go` call the `service_*.go` functions, which call `auth`, `bookmarks` and `users`.

The distroless image has no shell or `curl`, so the Dockerfile sets no `HEALTHCHECK`; probe it from the orchestrator or proxy.

### linkding-compatible API (`internal/server/linkding_*.go`)

A subset of linkding's REST API for programs that already speak it (browser extensions, mobile apps). Paths keep linkding's trailing slash and are mounted by `mountLinkding`, next to `mountAPI`. They do not overlap the routes above: the mux anchors them with `{$}`, and the literal `check/` wins over `{id}/`.

- Authentication is `Authorization: Token <token>` and nothing else (`tokenGuarded`, `userFromToken`). A cookie or a forwarded user is not read, so a request without the header is 401 even from a signed-in browser. These routes skip `sameOriginOnly`: an extension sends `Origin: chrome-extension://…`, and that check protects a cookie, which these routes do not accept. The messages and the `WWW-Authenticate: Token` header are those of Django REST framework's token authentication: no header or another scheme, `Token` alone, a token with spaces, an unknown token. The keyword is case-insensitive.
- Errors are `{"detail": "..."}`, not bkd's `{"error": "..."}`: 400, 401, 404 (`Not found.`, also for an id that is not a number) and 500 (the cause is logged, never sent). A method the route does not have is bkd's empty 405 with `Allow`; linkding answers it with JSON.
- A list is `{count, next, previous, results}`. `limit` is 100 by default and at most 1000; a `limit` or `offset` that is not a number, or a `limit` below 1, is the default and not an error (as in Django REST framework). `next` and `previous` are absolute URLs of the same request with the page moved: `https` when the connection is TLS or `--secure-cookies` is on, else `http`, and the host is the request's `Host` (behind a proxy, let it pass `Host`). `next` is `null` when `offset + limit >= count`; `previous` drops `offset` when it would reach the first page.
- A bookmark is linkding's JSON. `description` is bkd's `site.description` (what the page says), `notes` is bkd's `note`, and `website_title` and `website_description` are the site's fields, `null` when empty. `is_archived`, `unread` and `shared` are `false`, `web_archive_snapshot_url` is `""`, `favicon_url` and `preview_image_url` are `null`: bkd has none of these. `date_added` and `date_modified` are `created_at` and `updated_at` as `2006-01-02T15:04:05.000000Z` in UTC.
- `q` is bkd's search syntax, not linkding's (`#tag` and `!archived` mean nothing here). `added_since` and `modified_since` take RFC 3339, the same without a zone (UTC), with a space for the `T`, or a date; anything else is 400. The comparison is strictly after, on whole seconds rounded down, because bkd keeps seconds (`bookmarks.Since` adds `created_at > ?` and `updated_at > ?` to the filter).
- `GET /api/tags/` has no tag table behind it, so `id` is made up: the tag's rank among the user's tags by name, stable only while the set of tags is. `date_added` is the `created_at` of the oldest bookmark that carries the tag. Order is by name.
- `GET /api/bookmarks/check/?url=` answers `{bookmark, metadata, auto_tags}`. `bookmark` is the user's oldest bookmark with exactly that URL (trimmed, no normalising) or `null`; `metadata.title` and `.description` are the stored site details of that bookmark, `null` for an address that is not bookmarked. bkd does not fetch the page here, and `auto_tags` is always empty. A missing or empty `url` is 400.
- Only reading exists. Creating, changing and deleting go through bkd's own `/api/bookmarks` routes with a session.

### Import and export (`internal/netscape`, `internal/importer`, `internal/server/api_transfer.go`)

- **Format.** Import reads the Netscape bookmark HTML that Chrome, Firefox, Safari, Pocket and Raindrop export. `internal/netscape` is a small tolerant tokenizer, not an HTML parser: it knows `A`, `H3`, `DL`, `DD` and `BR`, decodes entities, and survives unclosed tags and truncated input. This avoids a large HTML dependency for a fixed, tiny grammar.
- **Mapping.** Each folder level above a link becomes one tag, and the `TAGS` attribute adds more. `ADD_DATE` (or Pocket's `time_added`) becomes `created_at` (milliseconds and microseconds are scaled down; a missing, zero, negative or future date becomes now). A `<DD>` right after a link is its note.
- **Rules.** Every link goes through the same validation as `POST /api/bookmarks`, with one difference (`bookmarks.Fitted`): an over-long title, note or tag set is shortened and an unusable tag is dropped, instead of refusing the whole link. A missing title falls back to the URL. A link that is not `http(s)` (`javascript:`, `place:`, `about:`) is skipped and counted, and the report names the first five.
- **Duplicates.** A URL the user already has, or that appears twice in the file, is skipped, so importing the same file twice adds nothing. The match is on the exact URL string, per user.
- **Transaction.** The whole file is inserted in one `BEGIN IMMEDIATE` transaction: a failure leaves nothing behind, and a concurrent write cannot make the upgrade to a writer fail. The write lock is held for the whole insert, so a very large file briefly delays other users' writes.
- **Limits.** The import route accepts up to 20 MiB; every other route keeps 64 KiB.
- **CSRF.** The import body is not JSON, so the route requires `Content-Type: text/html` (else 415). A cross-site form cannot send that type, and a script that sets it needs a CORS preflight, which the server never answers. The `Origin` check still applies.
- **Export.** HTML is a flat file with each bookmark's tags in `TAGS`, in the order created; a comma inside a tag becomes a space so it cannot split. JSON has `url`, `title`, `note`, `tags` and `created_at`. Both contain only the caller's bookmarks. JSON is a backup; only HTML is imported.

### User management

- There is no public registration and no command-line recovery, so the system must never lose its last active admin. Demoting, disabling or deleting an admin runs in a `BEGIN IMMEDIATE` transaction that first checks another active admin remains; otherwise the API answers 409. Two admins removing each other at the same moment are serialized, so exactly one succeeds. A disabled admin does not count.
- An admin may demote, disable or delete themselves while another active admin remains.
- Disabling, password reset and a password change delete every session and API token of the user in the same transaction (`revokeEveryCredential`). A password change ends tokens too because a stolen cookie can make a token that outlives every session. Enabling again does not bring old sessions or tokens back. `APITokens.Create` is one statement that checks the account is active, the asking session still exists (a proxy user has none) and the user holds fewer than 20 tokens, so a request that was accepted before a reset or disable, and is still being read, cannot make a token afterwards (`ErrCallerGone`, answered 401).
- Hashing a password takes tens of milliseconds, and an admin may be demoted in that gap. Each `users.*` change therefore re-checks inside its transaction that the caller is still an active admin. Login does the same: `Sessions.CreateIfUnchanged` inserts the session only if the account is still active and still has the verified hash, so a reset or disable that lands during verification cannot be followed by a session.
- `adminUser` reads the role from the database on every request, so a demoted admin is refused at once (403; 401 when not signed in).

- **Ownership.** Every bookmark query carries the session's `user_id`. A bookmark that belongs to someone else answers 404, the same as a missing one.
- **Validation** (`internal/bookmarks`). URLs must be `http://` or `https://` because the front end renders them as links, and a `javascript:` URL would run script. Tags are trimmed, lowercased and deduplicated. Only a validated `bookmarks.Input` can be stored.
- **Link check** (`internal/linkcheck`). The server makes requests to addresses users choose, so the SSRF rule is the core of the module: only public addresses are contacted. A filtering dialer resolves the name once, drops every non-public address from the answers and connects to one of the rest, so a second DNS answer cannot change where it connects (no rebinding). IP literals in the URL and in every redirect are checked by `guard.allowsURL`, because the dialer never sees a name for them. IPv4-mapped IPv6 is judged as its IPv4 address. No proxy is used. Only tests build a checker that allows loopback (`Config.Allow`); production uses `linkcheck.New(linkcheck.Config{})`. Targets on one host run one after another; a global semaphore caps requests in flight. The route is a server-sent event stream (POST, so the front end reads it with `fetch`, not `EventSource`): the stream owns the running check and the user's slot, so a client that disconnects or presses Stop drops both and the unfinished requests are aborted. The result (`link_status`, `link_checked_at`, `link_detail`) is stored with a `WHERE url = ?` guard, so an edit during the check is not overwritten, and `bookmarks.Store.Update` clears it when the URL changes. Search reads it with `status:`, and the list and random routes take a `status` parameter for the sidebar's Status filter (`GET /api/tags` also returns `links`, the count per result); `COALESCE(link_status, 'unchecked')` keeps `-status:broken` from dropping bookmarks never checked. Requests to one site are made in turn; a host that answers 429 or 503, or times out twice in a row, is not asked again in that check (its other targets come back as skipped; the verdict carries a `Backoff` with `Host` and `RetryAfter`, where `Host` is the site that answered after redirects, and the group stops only when it is the group's own host). One bookmark has a 10 second budget for HEAD and GET together (a timeout is not retried with GET). The streaming route has no total deadline, because results arrive one by one and Stop works; the no-script path (the page handler in `pages_bulk.go`) is one response, so it gives up after 45 seconds and redirects with the `check-incomplete` notice. Also, a `cf-mitigated: challenge` answer is "unknown" and skips the GET. `hostOf` drops a leading `www.` so both spellings count as one site.
- **Background link check** (`internal/backgroundcheck`, `users.link_check_enabled`). Started from `cmd/bkd/serve.go` only when `--link-check-interval` is above 0; its context is cancelled when the server stops. Each round selects up to `--link-check-batch` bookmarks of active users who opted in (`ROW_NUMBER() OVER (PARTITION BY user_id ...)` makes users take turns; never-checked first, then oldest `link_checked_at`; anything checked in the last 7 days is skipped), checks them with `Checker.StartPaced` (1.5 s between requests to one host) and stores each verdict through the same `store` as the button, so the `WHERE url = ?` guard still applies. A host that returned a backoff goes into an in-memory map of cooldowns (strikes and an end time), keyed on the answering host; its bookmarks are skipped until the wait ends and are picked up again by a later round. The wait is `Retry-After` when given, else 60 s doubling per strike in a row; both are capped at 24 hours, and a normal answer from the bookmarked host removes the entry. The map is not persisted, so a restart forgets it. The user setting lives on `users` (not a settings table) and is read through `users.LinkCheckEnabled` and written with `users.SetLinkCheck` (with the User-Agent below); `/settings` (page) and `/api/settings` are open to every signed-in user, including proxy users, which is why it is not on the Account page. `App.backgroundOn` (from `Config.BackgroundLinkCheck`) only lets the page say that the server has the check off.
- **Link check User-Agent** (`users.link_check_user_agent`, migration 0006). One `Checker` serves every user, so the User-Agent travels with each `linkcheck.Target` (`Target.UserAgent`; empty means `linkcheck.DefaultUserAgent()`) into `Inspect` and from there into both the HEAD and the GET. `linkcheck.Store.Targets` joins `users` for the manual check, and `backgroundcheck.dueBookmarks` selects it for the background one, so the two paths cannot disagree. The value is user-supplied text that ends up in a request header: `linkcheck.ValidateUserAgent` trims it and allows printable ASCII (0x20 to 0x7E) up to 200 characters only, so a line break can never start another header (net/http would refuse it too, which would turn every check into "could not connect"), and the settings page escapes it like any other text. Validation runs before the write and both settings go in one `UPDATE` (`users.SetLinkCheck`), so a refused or failed `PUT /api/settings` changes nothing; a form post without the box (`POST /settings`) keeps the stored User-Agent, as an absent JSON field does. The Go-only migration is the first one after the Rust ones, so once it has run the Rust binary no longer starts on that database; `internal/db/migrate_test.go` compares a new database with `rustMigrations` and `rustSchema` plus `goOnlyMigrations` and `withGoOnlyChanges`, so the next Go-only migration updates both.
- **Page details** (`internal/sitemeta`, `linkcheck.Checker.ReadPage`, `internal/server/service_site.go`, `api_site.go`, `internal/views/site_fields.go`, migration `0007_site_metadata.sql`). The add and edit forms (`data-site-preview`) call `POST /api/site-preview` from `app.js` when the address changes (`input` after a 500 ms pause, `change` at once; one request in flight per form, the answer for an address that was typed over is dropped and the field's current address is read; the request is not aborted, because an abort races the release of the user's slot and the next request would get 429; a failure that is the page's own is remembered per address and not repeated, one that is not (429, no answer) is tried again on the next change; a submit while a read is pending or running is held back, for at most 5 seconds, and sent again with `requestSubmit` once the read ends, so a blank title is not saved as the domain only because the person was fast). The title and note placeholders show the site's title and description, and three hidden fields (`site_url`, `site_title`, `site_description`) carry them back with the form. The server fills a blank title with the site title, else the domain, and a blank note with the site description (`firstFilled` in `pages_bookmarks.go`); the details go to `bookmarks.site_title` and `bookmarks.site_description`, apart from the user's own `title` and `note`, which they never overwrite later. `Bookmark.Site` is `null` until a page was read and is appended after `link` in the JSON, since field order is part of the API. Trust: the hidden fields come from the client, so `bookmarkForm.site()` accepts them only when `site_url` equals the posted `url` (both trimmed); otherwise they are dropped, which is also what a form without script produces. They are only text, cut at 300 and 500 characters by `Site.Fitted()` (in `bookmarkForm.site()` before a blank title or note takes them, since a title over the limit would be refused although the person wrote nothing; in `sitePreview`, so that the placeholders show what is saved; and in `Validate`), and nothing is fetched on save, so a client can make bkd store a wrong description for its own bookmark but cannot make the server contact anything. `Store.Update` replaces the stored details when the URL changes, and with the same URL only when the form sent some (`CASE WHEN url = ?1 AND NOT ?9 THEN site_title ELSE NULLIF(?7, '') END`, `?9` being "the posted `Site` is not empty"; both columns go together, since a title and a description from two readings do not describe one page). The edit form echoes the stored details in its hidden fields, so an ordinary save writes them back unchanged, and "Read the page again" (`button[data-site-reread]`, hidden until the script runs; `rereadSiteDetails` in `app.js` clears the failure memo and starts a read that does not look at whether the details are already there) puts the new ones there: nothing is stored before the form is sent. A page that says nothing posts empty details, which keep what was stored, so a re-read never erases anything (if the person also cleared the title, it is saved as the domain, since the stored title is not posted back as text); the JSON API posts none and keeps them too. Because the edit form echoes the stored details, every save from it writes them, so a form opened before another tab re-read the page puts the older details back: last writer wins, as for title and note, and nothing else writes the details in the background. `Create` stores what was posted; import and the JSON API post none. The fetch is `ReadPage(ctx, address, userAgent)`, so the SSRF guard, the 16 request slots and the 10 second budget are the link check's, not a second copy; it sends a GET with the user's User-Agent (`users.LinkCheckUserAgent`, empty means `DefaultUserAgent()`) and `Accept: text/html,application/xhtml+xml`, refuses a bot check, a non-2xx answer and a non-HTML type (an absent type is accepted), and keeps the first 512 KiB (`io.LimitReader`), which bounds the memory of the 16 slots. `PageError` carries the detail text shown to the user (`Address is not public`, `HTTP 404`, ...) and is never a raw error string. `sitemeta.Parse` does no network I/O: it runs `golang.org/x/net/html`'s tokenizer over the head and stops at `<body>`, prefers `og:title` and `og:description` (matched through `property` or `name`, case-insensitively) to `<title>` and `meta name=description`, takes the first non-empty value of each, and cleans it to one line (`ToValidUTF8`, Bidi and other control characters removed, whitespace collapsed). Non-UTF-8 pages are only made valid, not transcoded, and `og:image` is not read (the CSP and privacy). `sitePreview` holds the user's `ActiveChecks` slot for the whole read, so one user has one outbound read at a time, whether it is a check, a preview or a bulk read. The list does not show or search the details. **Bulk "Read pages"** (bookmarks made by import or the JSON API have no details, and the edit form's button reads one bookmark at a time): the bulk bar's `read` action runs `Checker.StartReads`, which is `StartPaced` with another inspect function (`hostRun.inspect`), so it keeps the check's rules: hosts in parallel (4), one host's pages one after another, a 429 or 503 or two timeouts in a row skip the rest of that host. `inspectRead` parses the body at once (`sitemeta.Parse`) and keeps only `Inspection.Meta`, each text cut at 1000 characters (`maxReadMetaChars`, above what a bookmark keeps), so a batch does not hold up to 200 pages of 512 KiB in memory while it is collected. `Store.SetSite` writes both detail columns as a unit and fills the note with the description only when the note is exactly blank; it never touches the title, a note that has text, or `updated_at` (a batch of reads is not an edit by the user and must not reorder the list), and it is guarded by `url = ?`, the address that was read, so a bookmark edited during the read keeps the details of its new address (no event is sent for it). A page that says nothing stores nothing, so a read never erases details. The stream shares `claimTargets` and `streamEvents` with the link check (`api_check.go`); without a script `pageBulk` runs the same targets through `runPosted` with a `postedRun` (`linkCheckRun` or `pageReadRun`) and answers with the notice `bulk-done` for a link check (`check-incomplete` when a link was left out), while a read that did not get to every page (could not be read, skipped, or out of time) shows the list again in select mode (`bulkUnread`, status 200) with only those rows ticked and a message with their number, since a redirect cannot carry the rows. In `app.js` the check and the read are two entries of `STREAMS` (URL, label, event handlers, summary, texts) over one `runStream`. The bulk read does not show its results in the list, since details are not listed: the notes it filled appear when the list is loaded again at the end, and the summary counts them.
- **Bulk actions** (`internal/bookmarks/bulk.go`). Ownership of every id is checked inside the transaction (`count(*)` of the caller's rows must equal the number of ids), so another user's id behaves like a missing one and nothing leaks or half-applies. Tag rules are the ones in `bookmark.go`; the 20-tag limit is checked after the inserts and rolls the batch back. The bulk form posts the ticked rows of the rows shown (`id-<n>`), and select mode ends after an action.
- **Search** (`internal/search`). `LIKE` with `ESCAPE`, so `%`, `_` and `\` in the query are literal. `q` is parsed into terms (`"phrase"`, `-exclude`, `title:`/`url:`/`note:`/`tag:` prefixes, max 8 terms of 100 chars); every term must match. A plain term matches title, URL, note or a tag; a prefixed term matches that field only, and `tag:` is an exact, case-insensitive tag match. `LIKE` ignores case for ASCII only. Dynamic SQL contains only placeholders; user text is always bound. `Filter.Highlights` gives the terms to highlight per field; `TestParseAgreesWithTheRustParser` in `internal/search/search_test.go` holds the cases captured from the Rust parser.
- **CSRF.** Three layers: `SameSite=Lax` on the cookie, JSON-only bodies (a form post gets 415), and a check that a state-changing request's `Origin`, if present, equals `Host`. Requests without `Origin` (command-line clients) pass.
- **Rate limits.** Login: 10 attempts per minute per IP. Setup: 5. Successful attempts are refunded; failures are not.
- **Client address.** The peer address of the TCP connection. `X-Forwarded-For` is ignored, so behind a reverse proxy every client shares the proxy's address and one budget. Do not put bkd behind a proxy until trusted-proxy support exists.
- **Host header.** Writes (POST, PUT, DELETE) are refused with 403 when the `Origin` header does not equal `Host`. A proxy that rewrites `Host` breaks every write, so it must pass `Host` through unchanged.
- **Session cookie.** `bkd_session`, or `__Host-bkd_session` when `--secure-cookies` is on, so a sibling subdomain cannot plant a cookie.
- **Shutdown.** SIGTERM and Ctrl-C both stop the server. In-flight requests get 10 seconds to finish.
- **Confirmed admin.** Creating, promoting, demoting, disabling, resetting and deleting users need `confirmedAdmin`: the session must have typed its password in the last 5 minutes, else 403 with `code: "reauth_required"`. A login counts, so an admin who just signed in is not asked. A page route sends the admin to `/confirm`, which calls `POST /api/account/confirm` logic and returns to `/users`. A stolen admin cookie therefore cannot change accounts without the password.
- **Response headers.** Every response, API and static, carries `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` `same-origin`, and a restrictive `Permissions-Policy`. `Strict-Transport-Security` is added only with `--secure-cookies`.
- **Password work.** Argon2 runs at most as many times at once as there are CPU cores, so a burst of logins cannot exhaust memory.
- **Malformed input.** A body or query that cannot be parsed gets a plain-text 4xx response, not the JSON error format; statuses match the Rust server, wording may differ (see CLAUDE.md, "Accepted differences").
- **Responses** carry `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Bodies over 64 KiB are refused (20 MiB for the import route).
- **Setup token flow.** At startup, if no user exists, a token is generated and logged at WARN. It lives in memory and is cleared when the first admin is created, or when a request finds that someone else won the race.


## Browser tests (`e2e/`)

- A separate Go module (godog + chromedp, with its own vendored dependencies), not part of the root build, so `go test ./...` at the root never opens a browser. It is run with `cd e2e && go test -count=1 -v ./...`, and by the CI `e2e` job.
- The suite uses the built binary `bin/bkd` (built if missing), and each scenario starts it with a temporary database and a free port, together with its own Chrome. The link checker only contacts public addresses, so a scenario that needs a "moved" or "broken" result writes it into the database (`Server.SetLinkCheck`). The setup token is read from the log line the server prints at startup.
- A scenario sets up what it needs through the JSON API (`e2e/internal/harness/api.go`) and exercises the behavior it is about through the browser. Features: `features/*.feature`; step code: `steps_*_test.go`.
- Edit and Delete show only under a hovering pointer, so the browser is started with a fine-pointer setting and steps hover the row before clicking.
- The double-Enter scenarios slow `fetch` down and watch for `securitypolicyviolation`: the CSP's `form-action 'none'` keeps a native submission out of the address bar, so a missing `preventDefault` shows only as a violation.
- The responsive feature resizes the window through the DevTools protocol and checks the drawer, `inert`, the row actions and the icon-only controls (label kept in the name, small box) on a phone, and that no page scrolls sideways. The redesign feature checks Load more (address, no reload, focus, ticks), the heading and filter chips, the inline edit and delete in the random pick, and the "/" key; the page cancelling the "/" key press is read from the event, because the DevTools protocol types the character even after a cancelled key press. The keyboard feature checks where focus lands after the page rebuilds. Its focus step waits for the focus, then reads it again after 300 ms, because the browser drops focus from a just-hidden control only at its next frame.
- Every click goes through `clickUntil` (`e2e/internal/harness/click.go`): on CI, Chrome sometimes accepts a click and delivers no event, so it then dispatches a scripted `click()` and logs a `WARNING`.
