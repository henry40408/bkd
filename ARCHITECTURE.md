# Architecture

## Stack

Go with the standard library `net/http`, `database/sql` over a pure-Go SQLite driver, and `flag` for the command line. Pages are rendered on the server by an escaping string builder in `internal/views`; the CSS and a small enhancement script are in `internal/assets/static/`, compiled into the binary with `go:embed`: no Node build, no CGO. The binary `cmd/bkd` is thin; the code lives in `internal/` packages so tests build the handler directly (`server.New(config).Handler()`). The server was rewritten from Rust; the Rust server's behaviour is the specification, pinned by the captured values that remain in the tests.

## Database

`internal/db` opens the pool and runs the migrations in `internal/db/migrations/` at startup (`migrate.go`, embedded with `go:embed`). The runner writes the `_sqlx_migrations` table, descriptions and SHA-384 checksums exactly as the Rust server did, so an existing database opens unchanged (`createRustDatabase` in `migrate_test.go` pins it). A released migration file is never edited: add a new numbered file. SQL is plain `database/sql` with bound parameters.

Every connection uses WAL, `synchronous = NORMAL`, `foreign_keys = ON` and a 5 second busy timeout. SQLite ignores foreign keys unless each connection enables them, and the cascade deletes below depend on it.

### Schema

- `users`: `username` is 3 to 32 characters of `a-z`, `0-9`, `.`, `_`, `-`, starting and ending with a letter or digit (a `CHECK` enforces it). It is ASCII only because SQLite folds case for ASCII alone, so the `UNIQUE` constraint is case-insensitive on every database. `disabled_at` is a nullable timestamp; `NULL` means active.
- `sessions`: stores a hash of the cookie token, never the token. Deleted with the user.
- `api_tokens` (migration 0008): the same for a token a program sends as `Authorization: Token <token>`. The primary key is the token's SHA-256, `name` is the owner's label (1 to 100 characters), and `last_used_at` is `NULL` until the first use. A token does not expire: it ends when its owner ends it, or when the account is disabled, reset or deleted. Deleted with the user.
- `bookmarks`: every row belongs to one user. Every query must filter by `user_id`. The index `bookmarks_user_url` (migration 0009) is for `FindByURL`, which a browser extension asks on every page it opens.
- `bookmark_tags`: one row per tag. Deleted with the bookmark. The application trims and lowercases tags, because SQLite cannot fold non-ASCII case, so tags may be in any script.

Deleting a user deletes their sessions, bookmarks and tags (`ON DELETE CASCADE`). Timestamps are Unix seconds. Tables are `STRICT`, so a value of the wrong type is rejected.

### Portability

Only SQLite is supported. SQL stays plain so a PostgreSQL port would mostly change the id columns, the case-insensitive username handling and the transaction used to serialize first-admin creation. No database abstraction layer is used.

## Authentication (`internal/auth/`, `internal/users/`)

- `password`: Argon2id with the same parameters as the Rust server (stored PHC strings verify in both directions; `rustPasswordVectors` in `password_test.go`). New passwords need 12 characters (at most 256 bytes) and must not contain the username (compared in lowercase); login accepts any password up to 256 bytes, so an older, weaker password still works. Hashing runs in `Hasher`, which allows at most as many hashes at once as there are CPU cores. For an unknown or disabled user, login must call `Hasher.VerifyDummy` so response time does not reveal which usernames exist. `WarmUp` builds the dummy hash at startup.
- `session`: the cookie holds 256 random bits; the database holds only their SHA-256. Sessions last 30 days and also end after 7 days without use (`last_used_at`, moved forward at most once an hour). A session also records its IP address and `User-Agent` (cut to 200 characters) for the session list, and `confirmed_at`, the last time its owner typed the password (a login counts). Every lookup joins `users`, so a disabled account loses access at once and `is_admin` is never cached. Disabling, deleting or resetting the password of a user must call `RevokeAllForUser`.
- `apitoken`: a token is 256 random bits in hex and the database holds only its SHA-256 (`APITokens.Create` returns the secret once, `Lookup` finds the user by the hash). A token is a password that does not expire, so it must never be logged, listed or returned again after creation; its id for the owner is the first 16 hex digits of the hash, honoured only together with the owner's `user_id`. `Lookup` joins `users` with `disabled_at IS NULL`, so a disabled account loses its tokens' access at once, and records `last_used_at` at most once an hour; a failed write there never fails the request. A user holds at most 20, enforced inside the insert (`INSERT … SELECT … WHERE count < 20`), so two concurrent requests cannot pass the limit. `users.SetDisabled` (when disabling) and `users.ResetPassword` end every token in the same transaction as every session (`revokeEveryCredential`); `ChangeOwnPassword` ends both too, because a stolen cookie can make a token that would outlive every session. Management lives on the Settings page, which a user the proxy signed in may use too (the Sessions and Change password sections are left out for them, and the routes behind them refuse them with 403), and a proxy user may need a token most: a program cannot pass the proxy's sign-in page.
- `forwardauth`: a trusted proxy's `Remote-User` header signs a user in on that request alone: there is no cookie and no `sessions` row, so the proxy decides when the user leaves, and `SessionUser.ViaProxy` is true. The header counts only when the TCP peer (not `X-Forwarded-For`) is inside `--forward-auth-trusted-proxies`; it then wins over a cookie. An invalid name from a trusted proxy signs nobody in. `users.AdoptForwarded` finds or creates the account (password hash `!`, which no password verifies), refuses a disabled one, and, when an admin group is configured, sets `is_admin` from `Remote-Groups` on each request. It never demotes the last active admin, and without an admin group the first account of an empty table is the admin: the emptiness check and the insert are one statement in `BEGIN IMMEDIATE` (`db.WithImmediateTx`), like `CreateFirstAdmin`, so two first requests cannot both be admins. Creating it also drops the setup token. A proxy user has no password, so `confirmedAdmin` lets them through, and change-password, the two session routes and confirm answer 403 (`refuseProxyUser`). Without cookies, CSRF protection rests on `sameOriginOnly` and the JSON-only bodies.
- `setuptoken`: 50 random bits shown as `XXXXX-XXXXX` (Crockford base32). It lives only in memory and is compared as HMACs in constant time. Case, dashes and spaces are ignored, and `O`, `I`, `L` read as `0`, `1`, `1`.
- `firstadmin`: one `INSERT ... WHERE NOT EXISTS` inside `BEGIN IMMEDIATE`, so concurrent submissions create exactly one admin.
- `ratelimit`: per-IP, in memory. A caller charges an attempt before checking the secret and refunds it only on success, so parallel requests cannot all pass the check and a success cannot erase earlier failures. Clients are grouped by IPv4 address or IPv6 /64; IPv4-mapped IPv6 addresses count as IPv4. When 10,000 addresses are tracked, new ones are refused until some windows end.
- `username`: the same rules as the `CHECK` in the schema, with ASCII lowercasing first.

## Front end (`internal/views/`, `internal/server/pages_*.go`, `internal/assets/static/`)

- The server renders every page as HTML with the builder in `internal/views` (`html.go` escapes `& < > "` only, byte for byte what the Rust templates produced): `layout.go` has the frames and `errors.go` the shared errors. Each page is one exported function that returns a string. The builder escapes all text; the only unescaped output is the highlighted text, which splits the text first and escapes each part. The app works with JavaScript turned off: every action is a link or a form, and a test suite posts the forms without a script.
- `internal/assets/static/app.css` and `app.js` are served at `/app.css` and `/app.js` with `Cache-Control: no-cache`. `app.js` is progressive enhancement only: it turns a same-origin click or form submit into a `fetch`, parses the HTML answer with `DOMParser` and swaps `main` and the sidebar, keeping the history in step (`pushState`, `popstate`). If anything fails, it falls back to the normal navigation. It also shows `<time>` tooltips in the reader's time zone, grows the list in place on Load more (`replaceState`; ticked rows stay ticked, and a focused link moves the focus to the first new row), opens Edit and Delete as inline panels inside a list row or the random pick (the form is read from the edit or delete page and posted from there; a refusal stays in the panel, Escape or Keep closes it and returns the focus to the link), fills the edit form's URL field from the "Use new address" button of a moved link, makes "/" outside a field focus the search field, reveals what the server marks `data-script-only` (that button, the import drop hint) and lets a file be dropped on the import box. No page needs it.
- Real paths, not hash routes: `/` (the list; `q`, `tag`, `status`, `page`, `select=1`), `/random`, `/bookmarks/{id}/edit`, `/bookmarks/{id}/delete`, `/login`, `/setup`, `/confirm`, `/users`, `/transfer`, `/settings` (the one page of a user's own settings: link check, User-Agent, API tokens, and, for a user signed in with a password, the sessions and the password; with `POST /settings/tokens`, `POST /settings/tokens/{id}/revoke`, `POST /settings/password`, `POST /settings/sessions/{id}/revoke` and `POST /settings/sessions/revoke-others`; a made token is answered on the page itself with status 200, never redirected, so the secret is in no address or cookie; without the script the page's address is `/settings/tokens`, and a reload asks the browser to post again, which makes a second token), and `/account`, which only redirects (303) to `/settings`: the page it was is part of Settings now, and old bookmarks keep working. A form that fails answers with the form again and the error status; a form that works redirects (POST-redirect-GET) with a fixed `?notice=` key that the server maps to text, so a link cannot put words on the page.
- The page handlers and the API handlers share the `service_*.go` functions in `internal/server`, so the rules (rate limits, timing guards, session rules, `confirmedAdmin`) exist once. `signedInPage`, `adminPage` and `confirmedAdminPage` (`pages.go`) wrap the guards and turn a refusal into a redirect (`/login`, `/confirm`) or an error page. A page read without a session redirects to `/login?next=<path+query>`, with `&notice=session-ended` only when a session cookie came with the request; `next`, and the `back` value that Edit, Delete and their Cancel/Keep links carry to return to the list, are used only when `sameSitePath` accepts them (a path starting with a single `/`; no scheme, `//`, backslash or control character), else `/`. A refused bulk action shows the list again in select mode with the ticks and an error line.
- Without a script: `?page=N` is cumulative (the list shows the first N times the page size rows, and `bookmarks.Store.Count` gives the total for "Showing S of M"); a "Load more" link to `?page=N+1#bookmark-<id>` returns to the last row shown, and with the script it grows the list in place instead; select mode is `?select=1` with native checkboxes (`id-<n>`) in one bulk form; edit and delete use their own pages; "Check links" runs to the end before the page answers (with the script, it streams `POST /api/bookmarks/check` instead, shows "Checking links: n of N" with a Stop button that aborts the fetch, then reloads the page); Random shows the pick on the list; the mobile menu is a CSS checkbox; times are relative text with the UTC time as the tooltip.
- Pages carry a Content-Security-Policy with `form-action 'self'` and no inline script, style or event handler (a test checks this). `/app.js` and `/app.css` keep `form-action 'none'`.
- CSRF for forms: the session cookie is `SameSite=Lax` (a link from another site opens signed in; only top-level GETs carry it across sites, and no GET changes data), and `formOriginRequired` refuses a post unless its `Origin` equals `Host`. A browser sends `Origin: null` under `Referrer-Policy: no-referrer`, so pages send `Referrer-Policy: same-origin`. The four session routes under `/api` (below) still let a request without `Origin` through (only a script can send one).

## Web API (`internal/server/`)

bkd has no JSON API of its own. The pages are HTML forms; a person, a browser extension or a script that wants to read or change bookmarks uses the linkding-compatible API below, with an API token. Four routes under `/api` stay, only because `app.js` calls them with the session cookie (`mountAPI`); they are not a public interface. Handlers are thin: `api_*.go` call the `service_*.go` functions, which call `auth`, `bookmarks` and `users`.

| Route | Auth | Purpose |
| --- | --- | --- |
| `POST /api/bookmarks/check` | session | `{ids}`, 1 to 200; 404 and nothing checked if any id is missing or not the caller's; checks them (HEAD, then GET when HEAD does not succeed) and answers with server-sent events: `result` `{id, link: {status, checked_at, detail}}` per link checked, stored as it arrives; `skipped` `{id, reason: "slow_down" or "not_answering", host}` per link not asked (its host answered 429 or 503, or timed out twice in a row); then `done` |
| `POST /api/bookmarks/read` | session | `{ids}` as for `check` (same validation, 404, and one slot per user, shared with the check and `site-preview`: 429); reads each page with the owner's User-Agent (`linkcheck.Checker.StartReads`) and answers with server-sent events: `result` `{id, site: {title, description} or null, note_filled}` per page read (stored as it arrives by `Store.SetSite`; `site` is null, and nothing stored, when the page says nothing), `failed` `{id, detail}` per page that could not be read (nothing stored), `skipped` as for `check`; then `done`. A bookmark edited during the read gets no event, unless the page said nothing: then there was nothing to store, and `result` with a null `site` is sent without looking at the bookmark |
| `POST /api/site-preview` | session | `{url}`; reads that page with the caller's User-Agent (`linkcheck.Checker.ReadPage`) and answers `{title, description}`, empty strings when the page says nothing; 422 without `url`; 429 with `Retry-After` while the caller's check or another read runs (they share the `ActiveChecks` slot); 502 with `could not read the page: <detail>` when the page cannot be read or the address is not a public web address; nothing is stored |
| `GET /api/export?format=html\|json` | session | the user's own bookmarks as a download (`Content-Disposition: attachment`); the Import and export page links to it |
| `GET`/`POST /api/bookmarks/`, `GET`/`PUT`/`PATCH`/`DELETE /api/bookmarks/{id}/`, `GET /api/bookmarks/check/?url=`, `GET /api/bookmarks/archived/`, `GET /api/bookmarks/shared/`, `GET /api/tags/` | API token | the linkding-compatible API; see below |
| `GET /api/docs`, `GET /api/docs/openapi.json` and the files of the page | none | the Swagger UI and the OpenAPI document of that API; see "API documentation" |

Everything else is a form (`pages_*.go`, mounted by `mountPages`): sign in and out, setup, settings (`POST /settings`, and under `/settings/` the password, the sessions and the tokens), the users (`/users...`), bookmarks (create, edit, delete, bulk), `POST /confirm` and `POST /transfer/import`. A session route that is not signed in answers 401 with `{"error": ...}`; a page redirects to `/login` instead. `handleNotFound` answers an empty 404 for any other path under `/api`.

`GET /healthz` (outside `/api`, no auth) runs a database ping (`select 1` on a pooled connection): 200 `ok`, or 503 `unavailable` when it fails within 3 seconds, for example while every pooled connection is busy. It shows the pool is alive, not that the storage is healthy; allow a few failures in a row before restarting on it. The distroless image has no shell or `curl`, so the Dockerfile sets no `HEALTHCHECK`; probe it from the orchestrator or proxy.

### linkding-compatible API (`internal/server/linkding_*.go`)

A subset of linkding's REST API for programs that already speak it (browser extensions, mobile apps). Paths keep linkding's trailing slash and are mounted by `mountLinkding`, next to `mountAPI`. They do not overlap the routes above: the mux anchors them with `{$}`, and the literal `check/` wins over `{id}/`.

- Authentication is `Authorization: Token <token>` and nothing else (`tokenGuarded`, `userFromToken`). A cookie or a forwarded user is not read, so a request without the header is 401 even from a signed-in browser. These routes skip `sameOriginOnly`: an extension sends `Origin: chrome-extension://…`, and that check protects a cookie, which these routes do not accept. The messages and the `WWW-Authenticate: Token` header are those of Django REST framework's token authentication: no header or another scheme, `Token` alone, a token with spaces, an unknown token. The keyword is `Token` or `Bearer` (linkding takes both), in any case.
- Errors are `{"detail": "..."}`, not bkd's `{"error": "..."}`: 400, 401, 404 (`Not found.`, also for an id that is not a number), 413, 415, 422 and 500 (the cause is logged, never sent). A field that a write refused is `{"<field>": ["<message>"]}` (`apiError.field`, written by `writeDetailError`). A method the route does not have is bkd's empty 405 with `Allow`; linkding answers it with JSON.
- A list is `{count, next, previous, results}`. `limit` is 100 by default and at most 1000 (5000 for tags, what the official browser extension asks for); a `limit` or `offset` that is not a number, or a `limit` below 1, is the default and not an error (as in Django REST framework), and one too big for 64 bits is the maximum (`wholeNumber`). `next` and `previous` are absolute URLs of the same request with the page moved: `https` when the connection is TLS, `--secure-cookies` is on or `X-Forwarded-Proto` starts with `https` (believed only in that direction: a forged header can break a client's own link, and `http` would send its token in the clear), else `http`; the host is the request's `Host` (behind a proxy, let it pass `Host`). `next` is `null` when `offset + limit >= count`; `previous` drops `offset` when it would reach the first page.
- A bookmark is linkding's JSON. `description` is bkd's `site.description` (what the page says), `notes` is bkd's `note`, and `website_title` and `website_description` are the site's fields, `null` when empty. `is_archived`, `unread` and `shared` are `false`, `web_archive_snapshot_url` is `""`, `favicon_url` and `preview_image_url` are `null`: bkd has none of these. `date_added` and `date_modified` are `created_at` and `updated_at` as `2006-01-02T15:04:05.000000Z` in UTC.
- `q` is bkd's search syntax, not linkding's (`#tag` and `!archived` mean nothing here). `added_since` and `modified_since` take RFC 3339, the same without a zone (UTC), with a space for the `T`, without seconds, with an offset like `+0200`, or a date; an offset whose `+` was not encoded (the query string made it a space) is read as `+`; anything else is 400. The comparison is strictly after, on whole seconds rounded down, because bkd keeps seconds (`bookmarks.Since` adds `created_at > ?` and `updated_at > ?` to the filter).
- `GET /api/tags/` has no tag table behind it, so `id` is made up: 53 bits of the SHA-256 of the name (a JSON number holds that exactly), so it does not change when bookmarks are edited and is the same for every user. `date_added` is the `created_at` of the oldest bookmark that carries the tag. Order is by name.
- `GET /api/bookmarks/check/?url=` answers `{bookmark, metadata, auto_tags}`. `bookmark` is the user's bookmark with that URL (trimmed; a trailing slash is ignored, so `https://example.com/` finds `https://example.com`; the spelling asked for wins, then the lowest id) or `null`; `metadata.title` and `.description` are the stored site details of that bookmark, `null` for an address that is not bookmarked. bkd does not fetch the page here, and `auto_tags` is always empty. A missing or empty `url` is 400.
- `GET /api/bookmarks/archived/` and `/shared/` are empty lists: bkd has no archive and shares nothing, and an empty tab beats an error in a client.
- Writing is `linkding_write.go`. The body is `linkdingChange`: every field is a pointer, so a field that is left out (or `null`) is told from one sent empty. `POST` on an address the user already saved (`FindByURL`), `PUT` and `PATCH` share `changeLinkdingBookmark`: the stored bookmark with the sent fields laid over it, so a left-out field keeps its value. linkding blanks what a `POST` leaves out; bkd does not, because a client that sends only `url` would erase the notes and tags. `POST` answers 201 for both outcomes, keeps the stored spelling of the address and ignores the request's `url`; `PUT` needs `url`, `PATCH` does not; both answer 200. `DELETE` is 204 and goes through `deleteBookmark`, as the delete page does, so another user's id is 404.
- The shared rules are the pages': `createBookmark`, `deleteBookmark` and `Input.Validate` (through `validationFault`). `linkdingFaultOf` turns their messages into a field and a Django REST framework text (`Enter a valid URL.`, `This field is too long.`); a message it does not know stays `{"detail": ...}`. `This field is required.` and `This field may not be blank.` come from `linkdingChange.address()`, before any bkd rule runs. Limits are bkd's, not linkding's (title 300, notes 5000, description cut at 500, 20 tags of 50 characters).
- A blank `title` is not sent: a new bookmark gets `bookmarks.TitleFromURL` (the address cut to a title), a changed one keeps its title, because a bkd title cannot be empty. `description` is `Site.Description`. `UpdateRequest.ReplaceSite` lets an empty description clear the stored one; without it an empty `Site` means "not sent" and keeps the stored details. When the URL changes the stored details are replaced as on the edit page (the old page's title and description are dropped); a `description` sent with it becomes the new details.
- `PUT` and `PATCH` that change the URL to one of the user's other bookmarks are 400 `{"url": ["A bookmark with this URL already exists."]}`, checked with `FindByURL` (trailing slash ignored) before the update, because `bookmarks.url` has no unique index and the pages allow duplicates. A change that leaves the URL as it is is not checked, so a duplicate that already exists does not block editing the other fields.
- The linkding writes run one at a time (`App.linkdingWrites`, taken after the body is read, so a slow client does not hold it). Look-up and store are two transactions, and `bookmarks.url` has no unique index, so without it two `POST`s of one address both find nothing and both insert, which a client that retries does. It does not cover the pages: a note saved there between the `Get` and the `Update` of a `PATCH` is overwritten, as two concurrent edits on the edit page overwrite each other. A change of the address only by a trailing slash counts as a change (the new spelling is stored and the page details are dropped), though `POST` and the duplicate check treat the two as one address.
- `is_archived`, `unread`, `shared` and `?disable_scraping` are accepted and ignored: bkd has no archive, and never reads a page while it saves a bookmark (that is the explicit "Read pages" action).

### API documentation (`internal/apidocs`)

`GET /api/docs` (and `/api/docs/`) is a Swagger UI for the linkding-compatible API; `GET /api/docs/openapi.json` is the OpenAPI 3.0.3 document it shows. They need no token or sign-in (the description is public, and "Try it out" sends the token a person types into "Authorize"), answer GET only, and are mounted in `Handler` through `apidocs.Routes`, like the assets.

- `openapi.json` is written by hand and embedded. `info.x-linkding-version` says which linkding release it follows (`1.47.0`) and `info.version` is `linkding-v<that>`, so Swagger UI shows it next to the title; the README names the same version (a test holds them together, and fails on any `linkding v<x.y.z>` or `blob/v<x.y.z>/` mention in either file that names another). To follow a newer linkding: read its API documentation and serializers, change the document, then every mention of the version in `openapi.json` and the README. The document lists what linkding has and bkd does not answer, and every bkd difference is written in the field or operation it concerns; keep it in step with the README's list.
- Two tests in `internal/server/apidocs_test.go` keep the document honest. The routes it lists must be the routes `linkdingRoutes()` returns (the list `mountLinkding` mounts; a new route without a document entry, or the reverse, fails), and the real answers of the list, bookmark, tag and check routes must have exactly the fields their schemas say, with `null` only where the schema is `nullable`. Changing a response shape means changing the schema, or those tests fail.
- The Swagger UI files are `swagger-ui-bundle.js` and `swagger-ui.css` from the npm package `swagger-ui-dist` 5.35.0 (Apache-2.0), copied unchanged with its `LICENSE`, `NOTICE` and the bundle's licence list (all three are served beside the page, so the licence travels with the files); `static/SWAGGER_UI.md` has the version, the tarball's integrity hash and how to update. Nothing tracks them for updates, and `go-licenses` does not see them. The bundle is 1.7 MB, so the answer carries an `ETag` (`http.ServeContent` replies 304). `index.html` and `init.js` are bkd's own; the page has no inline script or style.
- The docs routes have their own Content Security Policy, the asset policy plus `img-src 'self' data:` (Swagger UI's style sheet draws its icons with `data:` images). No `unsafe-inline` or `unsafe-eval` is needed; if an update of Swagger UI needs either, do not add it: look for another way. The page loads nothing from another site, so it works without internet access.
- The page's files are named by absolute path (`/api/docs/...`), so bkd must be served at the root of its host, as everything else is.

### Import and export (`internal/netscape`, `internal/importer`, `internal/server/api_transfer.go`)

- **Format.** Import reads the Netscape bookmark HTML that Chrome, Firefox, Safari, Pocket and Raindrop export. `internal/netscape` is a small tolerant tokenizer, not an HTML parser: it knows `A`, `H3`, `DL`, `DD` and `BR`, decodes entities, and survives unclosed tags and truncated input. This avoids a large HTML dependency for a fixed, tiny grammar.
- **Mapping.** Each folder level above a link becomes one tag, and the `TAGS` attribute adds more. `ADD_DATE` (or Pocket's `time_added`) becomes `created_at` (milliseconds and microseconds are scaled down; a missing, zero, negative or future date becomes now). A `<DD>` right after a link is its note.
- **Rules.** Every link goes through the same validation as the create form, with one difference (`bookmarks.Fitted`): an over-long title, note or tag set is shortened and an unusable tag is dropped, instead of refusing the whole link. A missing title falls back to the URL. A link that is not `http(s)` (`javascript:`, `place:`, `about:`) is skipped and counted, and the report names the first five.
- **Duplicates.** A URL the user already has, or that appears twice in the file, is skipped, so importing the same file twice adds nothing. The match is on the exact URL string, per user.
- **Transaction.** The whole file is inserted in one `BEGIN IMMEDIATE` transaction: a failure leaves nothing behind, and a concurrent write cannot make the upgrade to a writer fail. The write lock is held for the whole insert, so a very large file briefly delays other users' writes.
- **Limits.** `POST /transfer/import` accepts up to 20 MiB; every other route keeps 64 KiB.
- **CSRF.** The import is a `multipart/form-data` form post with a `file` field, so it takes the same `formOriginRequired` check as every form: the post is refused unless its `Origin` equals `Host`.
- **Export.** HTML is a flat file with each bookmark's tags in `TAGS`, in the order created; a comma inside a tag becomes a space so it cannot split. JSON has `url`, `title`, `note`, `tags` and `created_at`. Both contain only the caller's bookmarks. JSON is a backup; only HTML is imported.

### User management

- There is no public registration and no command-line recovery, so the system must never lose its last active admin. Demoting, disabling or deleting an admin runs in a `BEGIN IMMEDIATE` transaction that first checks another active admin remains; otherwise the API answers 409. Two admins removing each other at the same moment are serialized, so exactly one succeeds. A disabled admin does not count.
- An admin may demote, disable or delete themselves while another active admin remains.
- Disabling, password reset and a password change delete every session and API token of the user in the same transaction (`revokeEveryCredential`). A password change ends tokens too because a stolen cookie can make a token that outlives every session. Enabling again does not bring old sessions or tokens back. `APITokens.Create` is one statement that checks the account is active, the asking session still exists (a proxy user has none) and the user holds fewer than 20 tokens, so a request that was accepted before a reset or disable, and is still being read, cannot make a token afterwards (`ErrCallerGone`, answered 401).
- Hashing a password takes tens of milliseconds, and an admin may be demoted in that gap. Each `users.*` change therefore re-checks inside its transaction that the caller is still an active admin. Login does the same: `Sessions.CreateIfUnchanged` inserts the session only if the account is still active and still has the verified hash, so a reset or disable that lands during verification cannot be followed by a session.
- `adminUser` reads the role from the database on every request, so a demoted admin is refused at once (403; 401 when not signed in).

- **Ownership.** Every bookmark query carries the session's `user_id`. A bookmark that belongs to someone else answers 404, the same as a missing one.
- **Validation** (`internal/bookmarks`). URLs must be `http://` or `https://` because the front end renders them as links, and a `javascript:` URL would run script. Tags are trimmed, lowercased and deduplicated. Only a validated `bookmarks.Input` can be stored.
- **Link check** (`internal/linkcheck`). The server makes requests to addresses users choose, so the SSRF rule is the core of the module: only public addresses are contacted. A filtering dialer resolves the name once, drops every non-public address from the answers and connects to one of the rest, so a second DNS answer cannot change where it connects (no rebinding). IP literals in the URL and in every redirect are checked by `guard.allowsURL`, because the dialer never sees a name for them. IPv4-mapped IPv6 is judged as its IPv4 address. No proxy is used. Only tests build a checker that allows loopback (`Config.Allow`); production uses `linkcheck.New(linkcheck.Config{})`. Targets on one host run one after another; a global semaphore caps requests in flight. The route is a server-sent event stream (POST, so the front end reads it with `fetch`, not `EventSource`): the stream owns the running check and the user's slot, so a client that disconnects or presses Stop drops both and the unfinished requests are aborted. The result (`link_status`, `link_checked_at`, `link_detail`) is stored with a `WHERE url = ?` guard, so an edit during the check is not overwritten, and `bookmarks.Store.Update` clears it when the URL changes. Search reads it with `status:`, and the list and random pages take a `status` parameter for the sidebar's Status filter; `COALESCE(link_status, 'unchecked')` keeps `-status:broken` from dropping bookmarks never checked. Requests to one site are made in turn; a host that answers 429 or 503, or times out twice in a row, is not asked again in that check (its other targets come back as skipped; the verdict carries a `Backoff` with `Host` and `RetryAfter`, where `Host` is the site that answered after redirects, and the group stops only when it is the group's own host). One bookmark has a 10 second budget for HEAD and GET together (a timeout is not retried with GET). The streaming route has no total deadline, because results arrive one by one and Stop works; the no-script path (the page handler in `pages_bulk.go`) is one response, so it gives up after 45 seconds and redirects with the `check-incomplete` notice. Also, a `cf-mitigated: challenge` answer is "unknown" and skips the GET. `hostOf` drops a leading `www.` so both spellings count as one site.
- **Background link check** (`internal/backgroundcheck`, `users.link_check_enabled`). Started from `cmd/bkd/serve.go` only when `--link-check-interval` is above 0; its context is cancelled when the server stops. Each round selects up to `--link-check-batch` bookmarks of active users who opted in (`ROW_NUMBER() OVER (PARTITION BY user_id ...)` makes users take turns; never-checked first, then oldest `link_checked_at`; anything checked in the last 7 days is skipped), checks them with `Checker.StartPaced` (1.5 s between requests to one host) and stores each verdict through the same `store` as the button, so the `WHERE url = ?` guard still applies. A host that returned a backoff goes into an in-memory map of cooldowns (strikes and an end time), keyed on the answering host; its bookmarks are skipped until the wait ends and are picked up again by a later round. The wait is `Retry-After` when given, else 60 s doubling per strike in a row; both are capped at 24 hours, and a normal answer from the bookmarked host removes the entry. The map is not persisted, so a restart forgets it. The user setting lives on `users` (not a settings table) and is read through `users.LinkCheckEnabled` and written with `users.SetLinkCheck` (with the User-Agent below); `/settings` is open to every signed-in user, including proxy users, unlike the password and the sessions, which a proxy user does not have. `App.backgroundOn` (from `Config.BackgroundLinkCheck`) only lets the page say that the server has the check off.
- **Link check User-Agent** (`users.link_check_user_agent`, migration 0006). One `Checker` serves every user, so the User-Agent travels with each `linkcheck.Target` (`Target.UserAgent`; empty means `linkcheck.DefaultUserAgent()`) into `Inspect` and from there into both the HEAD and the GET. `linkcheck.Store.Targets` joins `users` for the manual check, and `backgroundcheck.dueBookmarks` selects it for the background one, so the two paths cannot disagree. The value is user-supplied text that ends up in a request header: `linkcheck.ValidateUserAgent` trims it and allows printable ASCII (0x20 to 0x7E) up to 200 characters only, so a line break can never start another header (net/http would refuse it too, which would turn every check into "could not connect"), and the settings page escapes it like any other text. Validation runs before the write and both settings go in one `UPDATE` (`users.SetLinkCheck`), so a refused or failed `POST /settings` changes nothing; a form post without the box keeps the stored User-Agent. The Go-only migration is the first one after the Rust ones, so once it has run the Rust binary no longer starts on that database; `internal/db/migrate_test.go` compares a new database with `rustMigrations` and `rustSchema` plus `goOnlyMigrations` and `withGoOnlyChanges`, so the next Go-only migration updates both.
- **Page details** (`internal/sitemeta`, `linkcheck.Checker.ReadPage`, `internal/server/service_site.go`, `api_site.go`, `internal/views/site_fields.go`, migration `0007_site_metadata.sql`). The add and edit forms (`data-site-preview`) call `POST /api/site-preview` from `app.js` when the address changes (`input` after a 500 ms pause, `change` at once; one request in flight per form, the answer for an address that was typed over is dropped and the field's current address is read; the request is not aborted, because an abort races the release of the user's slot and the next request would get 429; a failure that is the page's own is remembered per address and not repeated, one that is not (429, no answer) is tried again on the next change; a submit while a read is pending or running is held back, for at most 5 seconds, and sent again with `requestSubmit` once the read ends, so a blank title is not saved as the domain only because the person was fast). The title and note placeholders show the site's title and description, and three hidden fields (`site_url`, `site_title`, `site_description`) carry them back with the form. The server fills a blank title with the site title, else the domain, and a blank note with the site description (`firstFilled` in `pages_bookmarks.go`); the details go to `bookmarks.site_title` and `bookmarks.site_description`, apart from the user's own `title` and `note`, which they never overwrite later. `Bookmark.Site` is `null` until a page was read and is appended after `link` in the JSON, since field order is part of the API. Trust: the hidden fields come from the client, so `bookmarkForm.site()` accepts them only when `site_url` equals the posted `url` (both trimmed); otherwise they are dropped, which is also what a form without script produces. They are only text, cut at 300 and 500 characters by `Site.Fitted()` (in `bookmarkForm.site()` before a blank title or note takes them, since a title over the limit would be refused although the person wrote nothing; in `sitePreview`, so that the placeholders show what is saved; and in `Validate`), and nothing is fetched on save, so a client can make bkd store a wrong description for its own bookmark but cannot make the server contact anything. `Store.Update` replaces the stored details when the URL changes, and with the same URL only when the form sent some (`CASE WHEN url = ?1 AND NOT ?9 THEN site_title ELSE NULLIF(?7, '') END`, `?9` being "the posted `Site` is not empty"; both columns go together, since a title and a description from two readings do not describe one page). The edit form echoes the stored details in its hidden fields, so an ordinary save writes them back unchanged, and "Read the page again" (`button[data-site-reread]`, hidden until the script runs; `rereadSiteDetails` in `app.js` clears the failure memo and starts a read that does not look at whether the details are already there) puts the new ones there: nothing is stored before the form is sent. A page that says nothing posts empty details, which keep what was stored, so a re-read never erases anything (if the person also cleared the title, it is saved as the domain, since the stored title is not posted back as text); a linkding write without a `description` keeps them too. Because the edit form echoes the stored details, every save from it writes them, so a form opened before another tab re-read the page puts the older details back: last writer wins, as for title and note, and nothing else writes the details in the background. `Create` stores what was posted; import posts none, and the linkding API posts only its `description`. The fetch is `ReadPage(ctx, address, userAgent)`, so the SSRF guard, the 16 request slots and the 10 second budget are the link check's, not a second copy; it sends a GET with the user's User-Agent (`users.LinkCheckUserAgent`, empty means `DefaultUserAgent()`) and `Accept: text/html,application/xhtml+xml`, refuses a bot check, a non-2xx answer and a non-HTML type (an absent type is accepted), and keeps the first 512 KiB (`io.LimitReader`), which bounds the memory of the 16 slots. `PageError` carries the detail text shown to the user (`Address is not public`, `HTTP 404`, ...) and is never a raw error string. `sitemeta.Parse` does no network I/O: it runs `golang.org/x/net/html`'s tokenizer over the head and stops at `<body>`, prefers `og:title` and `og:description` (matched through `property` or `name`, case-insensitively) to `<title>` and `meta name=description`, takes the first non-empty value of each, and cleans it to one line (`ToValidUTF8`, Bidi and other control characters removed, whitespace collapsed). Non-UTF-8 pages are only made valid, not transcoded, and `og:image` is not read (the CSP and privacy). `sitePreview` holds the user's `ActiveChecks` slot for the whole read, so one user has one outbound read at a time, whether it is a check, a preview or a bulk read. The list does not show or search the details. **Bulk "Read pages"** (bookmarks made by import or by the linkding API without a `description` have no details, and the edit form's button reads one bookmark at a time): the bulk bar's `read` action runs `Checker.StartReads`, which is `StartPaced` with another inspect function (`hostRun.inspect`), so it keeps the check's rules: hosts in parallel (4), one host's pages one after another, a 429 or 503 or two timeouts in a row skip the rest of that host. `inspectRead` parses the body at once (`sitemeta.Parse`) and keeps only `Inspection.Meta`, each text cut at 1000 characters (`maxReadMetaChars`, above what a bookmark keeps), so a batch does not hold up to 200 pages of 512 KiB in memory while it is collected. `Store.SetSite` writes both detail columns as a unit and fills the note with the description only when the note is exactly blank; it never touches the title or a note that has text. It moves `updated_at` only when a detail or the note changed (a read that finds the same details leaves it alone), so a program that syncs with `modified_since` sees what a read added; the list is ordered by `created_at`, so this does not reorder it. It is guarded by `url = ?`, the address that was read, so a bookmark edited during the read keeps the details of its new address (no event is sent for it). A page that says nothing stores nothing, so a read never erases details. The stream shares `claimTargets` and `streamEvents` with the link check (`api_check.go`); without a script `pageBulk` runs the same targets through `runPosted` with a `postedRun` (`linkCheckRun` or `pageReadRun`) and answers with the notice `bulk-done` for a link check (`check-incomplete` when a link was left out), while a read that did not get to every page (could not be read, skipped, or out of time) shows the list again in select mode (`bulkUnread`, status 200) with only those rows ticked and a message with their number, since a redirect cannot carry the rows. In `app.js` the check and the read are two entries of `STREAMS` (URL, label, event handlers, summary, texts) over one `runStream`. The bulk read does not show its results in the list, since details are not listed: the notes it filled appear when the list is loaded again at the end, and the summary counts them.
- **Bulk actions** (`internal/bookmarks/bulk.go`). Ownership of every id is checked inside the transaction (`count(*)` of the caller's rows must equal the number of ids), so another user's id behaves like a missing one and nothing leaks or half-applies. Tag rules are the ones in `bookmark.go`; the 20-tag limit is checked after the inserts and rolls the batch back. The bulk form posts the ticked rows of the rows shown (`id-<n>`), and select mode ends after an action.
- **Search** (`internal/search`). `LIKE` with `ESCAPE`, so `%`, `_` and `\` in the query are literal. `q` is parsed into terms (`"phrase"`, `-exclude`, `title:`/`url:`/`note:`/`tag:` prefixes, max 8 terms of 100 chars); every term must match. A plain term matches title, URL, note or a tag; a prefixed term matches that field only, and `tag:` is an exact, case-insensitive tag match. `LIKE` ignores case for ASCII only. Dynamic SQL contains only placeholders; user text is always bound. `Filter.Highlights` gives the terms to highlight per field; `TestParseAgreesWithTheRustParser` in `internal/search/search_test.go` holds the cases captured from the Rust parser.
- **CSRF.** Forms: `SameSite=Lax` on the cookie and `formOriginRequired`, which refuses a post unless its `Origin` equals `Host`. The session routes under `/api` take JSON only (a form post gets 415) and refuse a state-changing request whose `Origin`, if present, differs from `Host`; a request without `Origin` (command-line clients) passes. The token routes do not read the cookie, so there is nothing to forge.
- **Rate limits.** Login: 10 attempts per minute per IP. Setup: 5. Successful attempts are refunded; failures are not.
- **Client address.** The peer address of the TCP connection. `X-Forwarded-For` is ignored, so behind a reverse proxy every client shares the proxy's address and one budget. Do not put bkd behind a proxy until trusted-proxy support exists.
- **Host header.** Writes (POST, PUT, DELETE) are refused with 403 when the `Origin` header does not equal `Host`. A proxy that rewrites `Host` breaks every write, so it must pass `Host` through unchanged.
- **Session cookie.** `bkd_session`, or `__Host-bkd_session` when `--secure-cookies` is on, so a sibling subdomain cannot plant a cookie.
- **Shutdown.** SIGTERM and Ctrl-C both stop the server. In-flight requests get 10 seconds to finish.
- **Confirmed admin.** Creating, promoting, demoting, disabling, resetting and deleting users need `confirmedAdmin`: the session must have typed its password in the last 5 minutes, else the admin is sent to `/confirm` (`code: "reauth_required"` inside the service). A login counts, so an admin who just signed in is not asked. `POST /confirm` checks the password, sets `confirmed_at` for the session and returns to `/users`. A stolen admin cookie therefore cannot change accounts without the password.
- **Response headers.** Every response, API and static, carries `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (a page sends `same-origin`, see CSRF for forms), `Cross-Origin-Opener-Policy` and `Cross-Origin-Resource-Policy` `same-origin`, and a restrictive `Permissions-Policy`. `Strict-Transport-Security` is added only with `--secure-cookies`.
- **Password work.** Argon2 runs at most as many times at once as there are CPU cores, so a burst of logins cannot exhaust memory.
- **Malformed input.** A body or query that cannot be parsed gets a plain-text 4xx response; the linkding routes answer `{"detail": ...}`. Statuses match the Rust server where a route still exists, wording may differ (see CLAUDE.md, "Accepted differences").
- **Responses** carry `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Bodies over 64 KiB are refused (20 MiB for the import route).
- **Setup token flow.** At startup, if no user exists, a token is generated and logged at WARN. It lives in memory and is cleared when the first admin is created, or when a request finds that someone else won the race.


## Browser tests (`e2e/`)

- A separate Go module (godog + chromedp, with its own vendored dependencies), not part of the root build, so `go test ./...` at the root never opens a browser. It is run with `cd e2e && go test -count=1 -v ./...`, and by the CI `e2e` job.
- The suite uses the built binary `bin/bkd` (built if missing), and each scenario starts it with a temporary database and a free port, together with its own Chrome. The link checker only contacts public addresses, so a scenario that needs a "moved" or "broken" result writes it into the database (`Server.SetLinkCheck`). The setup token is read from the log line the server prints at startup.
- A scenario sets up what it needs through the forms and the surviving routes (`e2e/internal/harness/api.go`) and exercises the behavior it is about through the browser. Features: `features/*.feature`; step code: `steps_*_test.go`.
- Edit and Delete show only under a hovering pointer, so the browser is started with a fine-pointer setting and steps hover the row before clicking.
- The double-Enter scenarios slow `fetch` down and watch for `securitypolicyviolation`: the CSP's `form-action 'none'` keeps a native submission out of the address bar, so a missing `preventDefault` shows only as a violation.
- The responsive feature resizes the window through the DevTools protocol and checks the drawer, `inert`, the row actions and the icon-only controls (label kept in the name, small box) on a phone, and that no page scrolls sideways. The redesign feature checks Load more (address, no reload, focus, ticks), the heading and filter chips, the inline edit and delete in the random pick, and the "/" key; the page cancelling the "/" key press is read from the event, because the DevTools protocol types the character even after a cancelled key press. The keyboard feature checks where focus lands after the page rebuilds. Its focus step waits for the focus, then reads it again after 300 ms, because the browser drops focus from a just-hidden control only at its next frame.
- Every click goes through `clickUntil` (`e2e/internal/harness/click.go`): on CI, Chrome sometimes accepts a click and delivers no event, so it then dispatches a scripted `click()` and logs a `WARNING`.
